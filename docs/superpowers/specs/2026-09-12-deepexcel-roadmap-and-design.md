## 二、路线图总览

**前提（2026-09-12 决策）：**
- **代码签名暂不采购**（成本 + 企业资质门槛），且当前自签名方案要移除
- **用户注册与后续付费是必需的**，但分两步：先建地基（M2），等产品力到位再开计费（M6）

```
M1  v0.5   止血：安装可靠性           ✅ 已实现
M2  v0.6   账号体系 + 服务端地基 ★    ✅ 已实现（管理后台 UI 除外）
M3  v0.7   工作簿语义索引 ★           ✅ 已实现
M4  v0.8   执行前 Diff 预览           ✅ 已实现
M5  v0.9   可复用技能                 ✅ 已实现
M6  v1.0   计费开关（代理 + 支付）    ✅ 已实现（支付渠道待商户号）
────────────────────────────────────────────
挂起  代码签名 / 企业版 / WPS 能力对齐
```

**为什么账号排在能力之前（M2 而非更后）——三个理由：**

1. **它是唯一越晚做越贵的东西。** 每一个不带身份概念构建的客户端功能（技能库、遥测、配额），将来都要返工。语义索引晚三周只是晚三周，账号晚三个月是返工三个月。
2. **现在完全没有分发控制。** 拿到 ZIP 的人都能装，我们不知道有多少人在用、是谁。邀请码注册立刻解决这个问题。
3. **遥测几乎免费搭车。** 有了服务端和用户 ID，原本要单独立项的可观测性只是多几张表，M5 可以直接并入 M2。

**为什么计费拆到 M6 而不是跟 M2 一起做：** 现在收不了钱——不是技术问题，是产品问题。任务成功率还没测量过，定价没有依据，付费理由（技能库）还没做出来。M2 先把地基打对，M6 只是"打开开关"。

**并行机会：** M2 是服务端（FastAPI/Postgres）+ 少量客户端登录 UI，M3 是 C#/Python 客户端内部改造，两者技术栈几乎不重叠。如果能并行推进，整条线可以压缩约 3 周。

> - `scripts/build-repair.ps1`、`scripts/verify-install-sandbox.ps1`、`scripts/_test_package_release.py`

### M1.1 代码签名：暂缓采购，但**移除自签名证书**

**决策：** 不采购代码签名证书。但当前自签名方案不能原样保留。

**为什么自签名是负资产：** 现在要求用户运行 `Install-Internal-Certificate.cmd`，往系统根证书存储里装一个我们自己签发的 CA。该私钥一旦泄露，持有者可为**任意软件**签名并被用户机器无条件信任。为省掉一次"仍要运行"的点击，引入系统级信任风险——不划算。

| | 自签名 + 装根证书（当前） | **不签名 + 校验值（推荐）** |
|---|---|---|
| 用户操作 | 运行 cmd 装根证书 → 运行安装器 | 运行安装器 → "更多信息"→"仍要运行" |
| SmartScreen | 不拦 | 蓝屏警告，可放行 |
| 安全风险 | **系统根信任被污染** | 无 |
| 完整性校验 | 靠证书 | 发布页公布 SHA-256 |

**动作：** `package_release.py` 默认 `--allow-unsigned` 且必须输出 `SHA256SUMS.txt`；删除 `Install-Internal-Certificate.cmd` 与 `new-internal-signing-cert.ps1`；README 补充 SmartScreen 放行说明；MOTW 解除逻辑（commit `85c0e5a`）保留。

**重新评估时点：** (a) 公开分发；(b) M6 开始收费（**收费后签名基本是必需项**，付费用户看到"未知发布者"会显著影响转化）；(c) 出现因 SmartScreen 放弃安装的实际反馈。届时评估 Azure Trusted Signing（约 $10/月，但需可验证企业主体，新注册公司可能不满足资质，需提前确认）。

> **连带影响（重要）：** 客户端不签名 ⇒ 任何人可修改客户端。因此**权限与配额校验绝不能依赖客户端**。这条直接决定了 M6 必须走服务端代理——见 M2.3。

> **成本复核（30 分钟内确认一下再定）：** 2023-06 之后所有代码签名证书都强制私钥存放于 FIPS 140-2 硬件，廉价软证书已不存在，市场底价就是 Azure Trusted Signing 的 ~$10/月（约 ¥850/年，无需硬件）。真正的门槛通常不是价格而是**主体资质**（可验证的企业实体，成立年限要求）。建议花半小时确认资质是否满足——如果能过，它比下面任何规避手段都划算；确认不满足再执行 M1.1b。

### M1.1b 无签名下的摩擦优化 ★

不签名的代价不是"装不上"，而是**每一步都在劝退**。按效果排序的优化手段：

#### 1. 内置自动更新器 —— 总摩擦降幅最大

**洞察：** SmartScreen 只拦从浏览器下载（带 MOTW）的文件。由**已安装程序自身**下载到本地并执行的更新包，不带 MOTW，不触发 SmartScreen。

所以：**首次安装痛一次，之后所有版本更新静默完成。** 考虑到 v0.4.11→v0.4.17 这种发版频率，这条的累积收益远超首装优化。顺带消灭了 README 里"删除旧 ZIP 和旧解压目录"这个纯人工步骤。

**安全要求（不可省）：** 没有 Authenticode 就没有系统级完整性校验，自动更新器不能盲目下载执行。做法——
- 客户端内嵌我们自己的 **Ed25519 公钥**
- 服务端发布 `update.json` 清单（版本号 + 下载 URL + SHA-256），用私钥签名
- 更新器：HTTPS 拉清单 → **验签** → 下载 → **校验 SHA-256** → 执行
- 这不是 Authenticode，但对"更新通道被投毒"这个实际威胁模型是足够的；私钥离线保管

这套机制天然接入 M2 的服务端，两者一起做边际成本很低。

#### 2. 杀毒软件误报白名单 —— 国内场景比 SmartScreen 更致命

SmartScreen 只是警告，用户还能放行；**360 / 火绒 / 腾讯电脑管家的误报会直接删文件或阻断安装**，而且用户完全不知道发生了什么。未签名 + 写注册表 + 释放 Python 运行时 + 启动子进程，是典型的高误报组合。

动作：
- 打包后用多引擎扫描自查（如 VirusTotal），记录每次发版的检出情况
- 向主流厂商提交误报申诉/白名单（国内：360、火绒、腾讯；国际：Microsoft WDSI 文件提交入口，免费）
- **绝不加壳**（UPX 等压缩壳是误报头号诱因）
- M1.2 的"安装器直写注册表、PowerShell 降级为开发工具"顺带大幅降低误报率——`powershell.exe` 写 `HKCU\...\Addins` 是杀软的经典告警模式

#### 3. 分发形态：直接给单个 EXE，不套 ZIP

当前流程 5 步：下载 ZIP → 删旧 ZIP 和旧目录 → 解压 → 装根证书 → 运行安装器。

改后 3 步：下载 EXE → 双击 → "更多信息"→"仍要运行"。

ZIP 套 EXE 并不能规避 SmartScreen（Windows 解压时会传播 MOTW），只是多一次解压。删掉 ZIP 层 + 删掉证书步骤 + 自动更新器接管旧版本清理，人工步骤从 5 降到 3，其中 2 步是"下载"和"双击"。

#### 4. 下载落地页配图文指引 —— 性价比最高的转化优化

用户面对蓝色"Windows 已保护你的电脑"会直接放弃，因为它看起来像病毒警告。文字说明没用，**要放截图并标红箭头指向"更多信息"**。

落地页最小要素：截图化的三步指引、SHA-256 校验值、一句话解释为什么会有这个提示、以及"我们没有购买代码签名证书"的坦诚说明。这比任何技术手段都更能提升首装完成率。

#### 5. 控制发版节奏 + 稳定下载源

- SmartScreen 声誉按**文件哈希**累积（没有证书就无法跨版本继承）。每发一个新版本，声誉归零重来。**自动更新器（第 1 条）恰好让大多数用户不再走浏览器下载路径**，这条的影响也随之减弱
- 下载 URL 保持稳定域名 + HTTPS；GitHub Releases 的下载信誉优于新注册的自有域名
- 小修小补合并发布，不要为单个 fix 发一个全量安装包

#### 6. 首装体验兜底

万一仍然失败（被杀软拦、SmartScreen 放行后仍无 Ribbon），`DeepExcel.Repair.exe`（M1.2）就是兜底。落地页上直接给出这个入口，而不是让用户来问。

**预期效果：** 首次安装从 5 步降到 3 步，且只痛这一次；后续所有更新零摩擦。剩余的不可消除摩擦就是一次"更多信息 → 仍要运行"——这是不签名的合理代价，用一张截图就能化解。

### M1.2 安装与加载的自检自愈 ★本里程碑核心

**问题根因：** COM 注册逻辑分散在 `register-user.ps1` 和安装器之间，任何一处失败都表现为"Excel 里没有 DeepExcel 选项卡"，用户无法自行诊断。7 个版本都栽在这里。

**三层防御：**

1. **安装器直写注册表**——Inno Setup 直接写 `HKCU\Software\Classes\CLSID\{...}` 与 `Addins\DeepExcel.AddIn\LoadBehavior=3`，PowerShell 脚本降级为开发期工具。**收敛到单一真相来源**是这里最关键的改动。
2. **加载项启动自检**——启动时校验注册表项、WebView2 Runtime、Python 运行时、Sidecar 可执行性，失败写结构化诊断码（如 `E-REG-001`）。
3. **独立修复器 `DeepExcel.Repair.exe`**——一键重注册 + 重置 `LoadBehavior` + 清理 `DisabledItems` + 清理孤儿 Python 进程 + 输出诊断包 ZIP。

**验收自动化（关键）：** Windows Sandbox 中跑全新安装 → 启动 Excel → 验证 Ribbon 存在 → 发一条指令 → 验证结果。每次发版必跑。约 3 天投入，直接终结"发版即回归"。

### M2.3 关键架构决策：出口路由抽象 ★★

**这是本次规划中最不可逆的一个决定。**

原 spec 的方案是"服务端下发真实 Claude API Key，客户端内存缓存不落盘"。**不要这样做。**

| | 下发真实 Key（原 spec） | **服务端代理（M6 目标）** |
|---|---|---|
| 计量计费 | 做不到——调用不经过我们 | 精确到 token |
| 配额限流 | 做不到 | 完整可控 |
| Key 泄露 | 客户端不签名，内存可 dump，泄露即全量损失 | 客户端永远拿不到真实 Key |
| 供应商切换/故障转移 | 需客户端发版 | 服务端热切换 |
| 成本 | 无额外开销 | 多一跳延迟 + 带宽 |

延迟代价可控：流式逐块透传，首 token 增加约 30–80ms，用户无感。而"无法计量"意味着**根本无法定价**——这是商业模式的地基问题，不是优化问题。加上客户端不签名、可被篡改，把权益判断留在客户端等于没有判断。

**但 M2 不需要现在就建代理。** M2 只需要做对一件事——**让"模型流量走哪里"由服务端在登录时决定，而不是客户端硬编码**：

```
登录成功 → 服务端返回 endpoint 配置
  {
    "mode": "byok",              // 当前阶段：用你自己的 Key
    "base_url": null,            // 客户端用本地 config.json 的供应商配置
    "auth": null
  }

M6 打开计费时，同一个接口改返回：
  {
    "mode": "hosted",            // 走我们的代理
    "base_url": "https://api.deepexcel.com/v1",
    "auth": "<短期 session token>"
  }
```

客户端 sidecar 只认这个响应，不关心背后是 BYOK 还是代理。**M6 从 BYOK 切到托管，客户端零改动。** 这个抽象成本极低（M2 多花约 2 天），省下的是 M6 的一次客户端大改 + 一轮全量发版。

**BYOK 长期保留**，不只是过渡：数据敏感的企业用户会要求模型流量不经过第三方，这是将来企业版的卖点，也是 M6 定价表里单独一档的理由。

### M2.4 遥测（并入本期，原独立里程碑取消）

有了服务端和用户 ID，遥测只是多两张表。

**隐私红线（不可妥协）：** 绝不上传单元格内容、工作簿名、文件路径、用户输入原文、API Key。

| 事件 | 字段 |
|---|---|
| `session_start` | 用户 ID、版本、Office 版本/位数、宿主（Excel/WPS） |
| `task_complete` | 会话 ID、工具调用序列（**仅工具名**）、耗时、token 用量、供应商与模型、结束状态 |
| `tool_error` | 工具名、错误分类码（**不含**错误消息原文，避免夹带数据） |
| `startup_error` | M1.2 定义的 `E-*` 诊断码 |
| `user_feedback` | 👍/👎 + 用户主动填写的文本 |

实现：sidecar 内批量缓冲，每 5 分钟或 20 条上报一次，**失败静默丢弃，绝不阻塞主流程**。注册流程中明确告知，配置中可关闭。

**保留一键诊断包导出**——用户遇到问题时打包本地日志 + 工具轨迹 + 环境信息（自动脱敏）。遥测看趋势，诊断包查个案，两者互补。

管理后台看板：DAU / **任务一次成功率** / 工具失败 TOP 10 / 供应商错误率 / 版本分布。

### M2.5 客户端改造

沿用 [2026-07-15 spec](2026-07-15-saas-client-integration-design.md)：登录面板 → `AuthClient` → `SessionManager` → sidecar 启动参数。补充：
- 未登录时功能禁用（UI 层面，**不作为安全边界**）
- 登录态持久化（refresh token 加密存 DPAPI，与 API Key 同机制）
- 离线宽限期：网络不可用时凭上次成功登录的缓存态继续工作 7 天，避免断网即瘫痪

### M2.6 北极星指标上线

M2 交付后第一次能回答：**任务一次成功率**（用户发出一条指令，无需人工修正即得到可用结果的比例）。这个数字是 M3~M5 所有优化的评判标准，也是 M6 定价的依据。

<details>
<summary>原始设计（保留）</summary>

**问题：** 当前模型靠 `read_range` 盲读数据推断表结构。表一大就要么读不全、要么 token 爆炸、要么猜错字段含义。这是任务失败的头号来源，也是用户说"AI 又改错地方了"的根因。

**方案：** 打开工作簿时后台构建轻量语义索引，作为系统上下文常驻：

```
Sheet "销售明细" (1..8420 行)
  表头行: 1
  A 订单号   text     唯一, 样例: "SO-2026-0001"
  B 日期     date     2026-01-01 ~ 2026-09-10
  C 客户     text     127 个不同值, 样例: "华东贸易"
  D 数量     number   1 ~ 500, 3 个空值(行 88, 402, 771)
  E 单价     number   带货币格式
  F 金额     formula  =D*E
  命名区域: 销售数据 = A1:F8420
  跨表引用: Sheet "产品表" 通过 A 列关联
```

**实现要点：**
- 复用已有 `WorkbookAnalyzer` / `RangeAnalyzer`，扩展为带类型推断与统计的索引器
- 增量更新：监听 `SheetChange`，只重算受影响列
- 大表采样：前 100 行 + 随机 500 行做统计，而非全量读取
- 索引缓存到 `%LOCALAPPDATA%\DeepExcel\index\`，按内容哈希失效
- 注入时机：作为 system prompt 一部分，随 `BuildContext` 下发

**成本与收益：** 单表约 300–600 token，远低于当前动辄几千 token 的盲读。这是唯一一个**同时**提升准确率、降低 token 成本、缩短响应时间的改动。M2 的遥测正好用来验证——看任务成功率是否真的上去了。

**风险：** 类型推断可能出错（混合类型列、多表头、合并单元格）。缓解：索引保留"置信度低"标记，低置信度时模型回退到实读；M4 的 Diff 预览是第二道防线。

</details>

## M4 — 执行前 Diff 预览（v0.8）　✅ 已实现（2026-09-12）

> **实现状态：**
> - `Preview/ChangePreview.cs` —— 变更集模型，「无法预览」是一等状态而非错误
> - `Preview/PreviewPolicy.cs` —— 三级确认：不问 / 精确预览 / 快照并告知
> - `Preview/PreviewBuilder.cs` —— 纯 diff 逻辑，不依赖 Excel 类型，可对刁钻场景测试
> - `Preview/ExcelRangeReader.cs` —— 块读取适配层
> - `PermissionDrawer` + `ChangePreview.tsx` —— 三种状态用不同边框色与徽章区分
>
> **两个关键设计：**
>
> 1. **「无法预览」必须与「精确预览」在视觉上分开。** 显示成同一种样子，用户很快
>    对前者也不再细看——而前者恰恰是唯一值得看的。VBA/Python 明确说"无法预知，
>    已快照"，不假装模拟过。
> 2. **「允许并记住」只适用于能力型授权。** 批准过一次 `delete_rows` 不等于批准
>    之后任何一次删除——下一次可能删 200 行。拆成 `_REMEMBERABLE_TOOLS`（VBA/
>    Python/send_keys）与逐次确认两类。
>
> **打扰与否的判断放在 C# 侧**，因为只有那边能看到工作簿当前状态：sidecar 对可能
> 有破坏性的操作一律询问，C# 算出变更集后，改 3 个单元格或根本没变化的自动放行。
>
> 顺手修掉一个自己引入的回归：把 `send_keys` 加入高风险集合后，Computer Use 的
> 触发词门禁被绕过——本该直接拒绝的调用变成了弹窗询问。门禁已前移。
>
> 测试 28 项（C#）+ 26 项（sidecar 权限策略）。

<details>
<summary>原始设计（保留）</summary>

### 原方案

**问题：** 当前是"先改后悔"——执行完才能回滚。用户对重要工作簿不敢用，这是使用频次的天花板。

**方案：** 高风险操作（批量写入、删行删列、公式替换、VBA/Python）先在内存计算变更集，展示改前/改后对比：

```
将修改 234 个单元格、删除 12 行
  C2   1200      → 1,200.00      (数字格式)
  C3   (空)      → 0
  行 88, 402…    → 删除
  ⚠ 3 处会覆盖已有公式
```

**实现要点：**
- 复用 `SnapshotManager`，快照时机从"执行后"**前移到"预演后"**
- 结构化工具可精确预演；VBA/Python 无法预演 → 退化为"强制快照 + 明确警告"，UI 上区分两种确认级别
- 大变更集只展示前 N 条 + 汇总统计
- 复用 `PermissionDrawer` 组件承载

**取舍：** 增加一次交互往返。建议可配置——低风险操作直接执行，高风险强制预览。这把 DeepExcel 从"玩具"变成"敢用在真实工作簿上的工具"，对留存的影响大于对流畅度的损害。

</details>

## M5 — 可复用技能（v0.9）　✅ 已实现（2026-09-12）

> **实现状态：**
> - `Skills/Skill.cs` —— 技能模型 + 重放提示词渲染
> - `Skills/SkillParameterizer.cs` —— 纯函数参数化：识别地址/日期/工作表/文件为变量
> - `Skills/SkillStore.cs` —— 一技能一文件的本地库（便于单文件分享、且单个损坏不影响其余）
> - `Bridge/SkillHandlers.cs` + `SkillPanel.tsx` —— 保存 / 列表 / 运行 / 删除
>
> **两个关键设计：**
>
> 1. **参数化的分寸。** 参数化过度，用户每次要把已经说过的话再说一遍；参数化不足，
>    技能只能在原始数据上跑。规则：地址/日期/工作表/文件路径 → 变量；排序方向、
>    是否有表头、图表类型 → 固定；**代码永不参数化**（占位符拼进 VBA 会让实际执行的
>    代码与被审核批准的代码不一致）。
> 2. **技能是骨架，不是宏。** 重放仍走 Agent，给的是「意图 + 上次成功的步骤」，
>    并明确要求"数据结构不符时以意图为准，不要机械重放"。逐字重放在数据稍有变化时
>    就会崩——而那是常态。
>
> 重放走的是普通消息路径，因此**同样经过 M4 的确认与变更预览**。如果重放能绕过这些
> 检查，技能库就成了绕过它们的途径。
>
> 测试 42 项（参数化 32 + 存储 10）。

<details>
<summary>原始设计（保留）</summary>

**问题：** 用户每月做同一份报表，每次都要重新描述一遍。DeepExcel 目前是"一次性对话"，不沉淀任何东西。

**方案：** 一次成功的多步任务完成后提示"保存为技能"。系统把工具调用序列参数化——区域、文件名、日期自动识别为变量——存为可命名、可一键重放、可分享的技能。

```
技能：月度销售报表
  参数：源数据区域(默认 A1:F*), 月份(默认当前月)
  步骤：清洗金额列 → 按地区汇总 → 建透视表 → 生成柱状图 → 套用格式
  [运行] [编辑] [分享]
```

**实现要点：**
- 技能 = 参数化的工具调用序列 + 可选的自然语言兜底步骤
- 数据源现成：`OperationHistory` 已记录工具调用序列
- 参数识别：单元格地址、日期、文件路径自动提升为变量，其余固化
- 执行时仍走 Agent，以技能为骨架，允许处理与录制时不同的数据形态
- 是现有 `PromptManager`（Slash Commands）的自然进化，UI 合并到同一入口
- **有了 M2 账号，技能可以云端同步与分享**——这是账号前置的又一处红利

**战略价值：** 技能库是**用户资产**，产生切换成本；技能分享是**增长飞轮**。这是 M6 最硬的付费理由——用户付的不是"AI 调用费"，是"我攒下来的自动化流程"。

</details>
