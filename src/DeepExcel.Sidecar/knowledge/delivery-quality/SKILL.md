# 交付质量与验证

用户看不到你调用了哪些工具，只看得到你说「做好了」。说之前必须自己验证过；验证不了的，就说验证不了。

## 一、写完之后必须回读

工具返回 success 只说明 Excel 接受了这次调用，不说明结果对。

- 写公式：回读几格计算结果（写后体检里的 samples 就是），看是不是期望的量级和符号。
  一整列公式至少看第一行、最后一行和中间一行。
- 写后体检（verification）报了新的 #REF! / #VALUE! / #DIV/0! / #N/A / #NAME?，或者 pattern_check
  报了孤立偏离、死值、合计漏行：先修，再汇报。不要把「有 3 个错误」留给用户自己发现。
- 批量改值（清洗、替换、填充）：对比改动前后的行数和非空格数。行数变了要能说清为什么。
- 删除行 / 去重：汇报删了多少行、依据是什么列；删之前的行数和删之后的行数都要说。

## 二、合计要对得上

- 分项之和 = 合计：新写的合计公式，拿分项用另一种方式（SUM 一整段 vs 逐项相加）核一次。
- 透视表 / 汇总表的总计应当等于源数据的总计。对不上时先查筛选、隐藏行、文本型数字。
- SUBTOTAL / AGGREGATE 会忽略被筛掉的行，SUM 不会：结果差了一截时先看有没有筛选。
- 文本型数字不参与 SUM：合计偏小、而单元格看起来都是数字时，用 find 或 inspect_sheet 查列类型。

## 三、不要留下隐患

- 公式列里混进手敲的数值（死值）：以后源数据一变，这一格不会跟着变。
- 本该是公式的地方写成了计算好的数值：用户以后改源数据，结果不会更新。除非用户要的就是「粘贴为值」。
- 引用用错了相对 / 绝对：向下填充后，看最后一行的公式引用是不是还指向该指的地方。
- 整列引用（A:A）放在 SUMPRODUCT、数组公式里会很慢；已用区域有明确边界时用具体范围。
- VBA 执行成功不等于做对了：执行后读一下它该改的区域。

## 四、汇报怎么写

1. 先说结论：做完了什么，结果在哪（表名 + 区域）。
2. 再说验证：怎么核对的、核对结果（「分项合计 1,234,567 与总计一致」）。
3. 如实说没做的和不确定的：「第 45 行日期格式无法识别，没有改，请你看一下」。
4. 有风险的操作提醒可以撤销：修改前自动备份过，可以在历史版本里回滚。

不要写：「已完成所有操作」「数据已全部正确」——除非你真的逐项核对过。
不要把工具的原始返回（JSON、英文报错）直接贴给用户，转述成用户能看懂的话。

## 五、做不到的时候

- 工具连续失败、同一个错误反复出现：停下来说清卡在哪里，给出你的判断和建议，问用户怎么办。
- 数据本身有问题（比如身份证号已经被科学计数法吞掉了后三位）：说明问题和原因，不要自己编造补全。
- 用户的要求有歧义（「把金额改成万元」是改显示还是改数值？）：先问，再动手。

## 常见报错

| 现象 | 常见原因 | 怎么办 |
|---|---|---|
| 写后体检报新增 #REF! | 公式引用了被删的行列或不存在的表 | 读出错格的公式，改引用 |
| 合计比预期小 | 文本型数字、筛选、隐藏行 | 查列类型；SUM 换 SUBTOTAL 前先确认用户要哪个 |
| 回读结果全是 0 | 引用错位（相对引用填充后偏移）、源区域是空的 | 读第一行和最后一行的公式对比 |
| 同样的错误连续出现 | 办法本身不对 | 换一种做法，或者问用户 |
